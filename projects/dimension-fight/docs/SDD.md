# SDD — Specification-Driven Development

## 1. 목적

이 프로젝트는 **Specification-Driven Development(SDD)** 방식으로 개발한다.

코드를 먼저 작성하지 않는다.

개발 전에 현재 상태와 요구사항을 이해하고, 구현해야 할 범위와 기준을 명확히 한 뒤 설계·구현·검증을 진행한다.

SDD의 목적은 다음과 같다.

- 요구사항의 잘못된 해석 방지
- AI의 임의 구현 방지
- 팀원 간 구현 기준 통일
- 불필요한 기능 추가 방지
- 설계와 코드의 불일치 감소
- 구현 완료 여부의 객관적 판단
- 요구사항 변경 사항의 지속적인 동기화
- 롤백할 상황을 항상 대비
- 트러블 슈팅 발생 시 노션에 정리, 특히 정형적 수치와 관련된 문제가 발생할 경우 제목에 (정형수치문제) 라고 명시하기
- 매일 작업한 것들은 개발일지로 프로젝트 내부에 폴더 하나 파서 기록하기

---

# 2. 전체 개발 흐름

모든 개발은 기본적으로 다음 순서를 따른다.

```
Explore
   ↓
Define
   ↓
Specify
   ↓
Design
   ↓
Consistency Check
   ↓
Plan
   ↓
Implement
   ↓
Verify
   ↓
Sync
```

단순한 오타나 문구 수정처럼 영향 범위가 매우 작은 작업은 일부 단계를 축소할 수 있다.

복잡하거나 여러 기능에 영향을 주는 작업은 전체 과정을 따른다.

---

# 3. 핵심 원칙

## 3.1 Understand Before Coding

코드를 수정하기 전에 현재 프로젝트 상태를 먼저 이해한다.

- 관련 파일 확인
- 기존 구현 확인
- 기존 데이터 흐름 확인
- 비슷한 기능 확인
- 프로젝트 구조 확인
- 영향을 받는 기능 확인
- API / DB / 외부 서비스 의존성 확인

분석하지 않은 코드의 동작을 추측하지 않는다.

---

## 3.2 Requirements First

모든 설계와 구현의 출발점은 요구사항이다.

기술을 사용하기 위해 기능을 설계하지 않는다.

```
기술
↓
기능 결정
```

이 아니라,

```
요구사항
↓
설계
↓
필요한 기술 선택
```

순서로 판단한다.

---

## 3.3 Do Not Assume

명확하지 않은 내용을 임의로 확정하지 않는다.

다음과 같은 경우 추측해서 구현하지 않는다.

- 요구사항이 여러 방식으로 해석되는 경우
- 문서 간 내용이 충돌하는 경우
- 기존 코드와 명세가 다른 경우
- 삭제 정책이 정의되지 않은 경우
- 상태 전이가 정의되지 않은 경우
- 인증/인가 기준이 불명확한 경우
- 새로운 기술 도입 여부가 결정되지 않은 경우

필요하면 해당 내용을 다음 중 하나로 분류한다.

```
확정
수정 필요
검토 필요
기획 결정 필요
```

`기획 결정 필요` 항목은 임의로 결정하지 않는다.

---

## 3.4 Scope Before Coding

구현 전에 현재 작업의 범위를 확인한다.

특히 다음을 구분한다.

```
In Scope
→ 이번 작업에서 변경해야 하는 것

Out of Scope
→ 이번 작업에서 변경하지 않는 것
```

요청하지 않은 기능을 임의로 추가하지 않는다.

미래에 필요할 것이라는 이유만으로 기능이나 구조를 미리 구현하지 않는다.

---

## 3.5 Simplicity First

현재 요구사항을 만족할 수 있는 가장 단순한 방법을 먼저 검토한다.

- 불필요한 추상화를 만들지 않는다.
- 필요하지 않은 Interface를 만들지 않는다.
- 한 번 사용하는 코드를 무조건 Utility로 분리하지 않는다.
- 필요하지 않은 Wrapper를 추가하지 않는다.
- 현재 문제를 해결하기 위해 지나치게 복잡한 구조를 만들지 않는다.
- 새로운 기술 도입 자체를 목표로 하지 않는다.

---

## 3.6 Surgical Changes

한 작업에서는 해당 요구사항과 관련된 부분만 수정한다.

- 관련 없는 코드 리팩토링 금지
- 요청하지 않은 파일 수정 금지
- 기존 기능 영향 범위 확인
- 한 작업에서 하나의 목적에 집중
- 가능한 최소한의 변경으로 구현

---

# 4. Source of Truth

프로젝트 설계와 구현은 확정된 문서를 기준으로 한다.

기본 우선순위:

```
1. 최신 요구사항
2. 최신 확정 기획
3. 최신 팀 의사결정
4. 확정 아키텍처
5. 확정 ERD
6. 확정 API 명세
7. 실제 코드
```

실제 코드가 존재한다고 해서 코드가 항상 최신 요구사항이라고 가정하지 않는다.

문서와 코드가 다르면 다음 순서로 확인한다.

```
차이 발견
   ↓
현재 코드 확인
   ↓
관련 문서 확인
   ↓
최신 결정 확인
   ↓
기준 확정
   ↓
수정
```

---

# 5. Explore

구현 전에 현재 시스템을 분석한다.

확인 대상:

- 관련 코드
- 프로젝트 구조
- 기존 구현 방식
- 유사 기능
- 데이터 흐름
- 상태 흐름
- API
- DB Schema
- 외부 서비스
- 테스트
- 영향받는 기능

핵심 질문:

> 현재 시스템은 어떻게 동작하고 있는가?
> 

현재 구조를 이해하기 전에는 구현을 시작하지 않는다.

---

# 6. Define

구현할 내용을 명확하게 정의한다.

다음 질문에 답할 수 있어야 한다.

```
왜 필요한가?
무엇을 해결하는가?
어디까지 구현하는가?
무엇은 구현하지 않는가?
누가 사용하는가?
어떤 결과가 나와야 하는가?
```

기능명만으로 구현을 시작하지 않는다.

예를 들어:

```
"로그인 구현"
```

만으로는 충분한 Specification이라고 판단하지 않는다.

기능의 목적과 완료 조건을 파악할 수 있어야 한다.

---

# 7. Specify

코드보다 먼저 시스템이 어떻게 동작해야 하는지를 명확하게 만든다.

Specification에는 필요한 수준에서 다음을 고려한다.

- 목적
- 범위
- 입력
- 출력
- 정상 흐름
- 실패 흐름
- 예외 상황
- 상태
- 제약조건
- 완료 조건

Specification의 핵심 기준은 다음과 같다.

> 사람이 읽었을 때와 AI가 읽었을 때 최대한 동일한 기능을 예상할 수 있어야 한다.
> 

---

# 8. Design

Specification이 충분히 명확해진 후 설계를 진행한다.

기본 흐름:

```
Requirements
      ↓
User Flow
      ↓
Domain
      ↓
State Flow
      ↓
Data Model
      ↓
API
      ↓
Implementation Structure
```

바로 Table, Entity, Controller 또는 Component부터 만들지 않는다.

---

# 9. Consistency Check

구현 전에 각 설계 요소가 서로 일치하는지 확인한다.

기본 검증 관계:

```
Requirements
      ↕
User Flow
      ↕
Domain
      ↕
State
      ↕
ERD / Data Model
      ↕
API
```

다음을 확인한다.

- 요구사항을 만족할 기능이 존재하는가?
- 기능에서 필요한 데이터가 존재하는가?
- 사용되지 않는 데이터가 존재하지 않는가?
- API와 데이터 구조가 일치하는가?
- 상태값이 서로 일치하는가?
- 동일 데이터가 불필요하게 중복되는가?
- 필요한 Validation이 존재하는가?
- 인증/인가가 필요한가?
- Transaction이 필요한가?
- 동시성 문제가 가능한가?
- 멱등성이 필요한가?
- 비동기 처리가 실제로 필요한가?
- 기존 기능에 영향을 주는가?

설계 간 모순이 있는 상태에서 구현을 진행하지 않는다.

---

# 10. Ambiguity Check

구현 전에 Specification의 모호성을 확인한다.

다음 질문을 기준으로 검토한다.

```
여러 방식으로 해석할 수 있는 부분이 있는가?

누락된 정상 상황이 있는가?

누락된 실패 상황이 있는가?

개발자가 임의로 결정해야 하는 부분이 있는가?

Frontend와 Backend가 다르게 이해할 가능성이 있는가?

구현 완료 여부를 판단하기 어려운 부분이 있는가?
```

AI는 가능하면 구현 전에 이러한 모호성을 먼저 찾아야 한다.

---

# 11. Plan Before Large Changes

영향 범위가 큰 작업은 바로 구현하지 않는다.

구현 전에 최소한 다음을 파악한다.

```
1. 현재 문제
2. 현재 구현 상태
3. 변경 대상
4. 구현 방법
5. 영향 범위
6. 위험 요소
7. 검증 방법
```

여러 파일이나 여러 Domain에 영향을 주는 작업은 Plan 없이 바로 수정하지 않는다.

---

# 12. Implement

구현은 확정된 Specification과 Design을 코드로 변환하는 과정이다.

다음 원칙을 따른다.

```
Specification에 정의된 것은 구현한다.

Specification에 없는 것은 임의로 구현하지 않는다.
```

구현 시:

- 기존 프로젝트 구조를 우선한다.
- 기존 네이밍과 스타일을 따른다.
- 필요한 부분만 수정한다.
- 새로운 구조가 반드시 필요한지 먼저 확인한다.
- 기존 기능을 가능한 유지한다.
- 하나의 작업에서 하나의 목적에 집중한다.

---

# 13. Definition of Done

코드가 작성됐다는 이유만으로 작업을 완료했다고 판단하지 않는다.

작업 완료 여부는 구현 전에 정한 조건을 기준으로 판단한다.

기본적으로 다음을 확인한다.

```
□ 요구사항을 충족했는가?

□ 정상 흐름이 동작하는가?

□ 주요 실패 흐름이 처리되는가?

□ API / 데이터 구조가 설계와 일치하는가?

□ 필요한 Validation이 적용됐는가?

□ Build가 성공하는가?

□ 관련 Test가 성공하는가?

□ 기존 기능이 정상 동작하는가?

□ 불필요한 코드나 파일이 생성되지 않았는가?
```

---

# 14. Verify Against Spec

검증의 기준은 작성된 코드가 아니라 Specification이다.

```
Specification
      ↓
Implementation
      ↓
Verification
```

검증 항목:

### Requirement

최초 요구사항을 충족했는가?

### Behavior

정의된 정상·실패 흐름대로 동작하는가?

### Build

프로젝트가 정상적으로 빌드되는가?

### Test

관련 테스트가 정상적으로 통과하는가?

### Regression

기존 기능이 깨지지 않았는가?

### API

Request / Response / Status Code가 설계와 일치하는가?

### Data

저장되는 데이터와 상태 전이가 올바른가?

검증하지 않은 내용을 성공했다고 말하지 않는다.

---

# 15. Measure Before Optimizing

성능 최적화는 추측으로 수행하지 않는다.

기본 순서:

```
Measure
   ↓
Find Bottleneck
   ↓
Analyze
   ↓
Improve
   ↓
Measure Again
```

근거 없이 다음을 추가하지 않는다.

- Cache
- Index
- Queue
- Batch
- Kafka
- Spark
- 분산 처리
- 새로운 Infrastructure

성능 개선을 주장할 경우 가능한 범위에서 수치로 확인한다.

---

# 16. Technology Adoption Rule

새로운 기술이나 라이브러리를 추가하기 전에 다음을 확인한다.

```
현재 기술로 해결할 수 없는가?

정말 필요한가?

더 단순한 방법은 없는가?

기존 구조와 충돌하지 않는가?

유지보수 비용이 지나치게 증가하지 않는가?
```

새로운 기술을 사용하기 위해 시스템을 복잡하게 만들지 않는다.

---

# 17. Change Management

구현 도중 요구사항이 변경될 수 있다.

요구사항이 변경되면 코드만 수정하지 않는다.

```
Requirement Change
        ↓
Specification Update
        ↓
Impact Analysis
        ↓
Design Update
        ↓
Implementation
        ↓
Test Update
        ↓
Verification
```

변경된 코드와 오래된 Specification을 동시에 유지하지 않는다.

---

# 18. Keep Spec and Code in Sync

Specification과 실제 구현은 지속적으로 동기화한다.

다음 상태를 방치하지 않는다.

```
Old Specification
        ≠
Current Code
```

구현 결과가 변경된 Specification을 기반으로 한다면 관련 문서도 최신 상태로 수정한다.

---

# 19. AI Development Rules

AI는 Specification을 기준으로 개발을 보조한다.

AI가 수행할 수 있는 작업:

- 기존 코드 분석
- 요구사항 분석
- Specification의 모호성 탐지
- 영향 범위 분석
- 구현 계획 작성
- 코드 구현
- 테스트 작성
- 구현 결과 검증
- Specification과 코드 비교

AI가 임의로 결정하지 않아야 하는 작업:

- 새로운 기능 추가
- 범위 확대
- 요구사항 변경
- Entity 임의 추가
- API 임의 추가
- 상태값 임의 추가
- 인증 구조 임의 변경
- 아키텍처 임의 변경
- 새로운 기술 임의 도입
- 아직 확정되지 않은 기획 결정

---

# 20. 작업 복잡도에 따른 적용 수준

모든 작업에 동일한 수준의 SDD를 적용하지 않는다.

## Simple

예:

- 문구 변경
- 오타 수정
- 단순 스타일 변경
- 명확한 이름 변경

필요한 단계만 간단하게 적용한다.

```
Understand
→ Change
→ Verify
```

---

## Normal

일반적인 기능 수정이나 추가:

```
Explore
→ Define
→ Specify
→ Plan
→ Implement
→ Verify
→ Sync
```

---

## Complex

다음과 같은 작업:

- 여러 Domain 영향
- DB Schema 변경
- 인증/인가
- 결제
- 예약
- AI 처리
- 외부 API
- 비동기 처리
- 동시성
- 핵심 데이터 변경
- 대규모 구조 변경

전체 SDD Flow를 적용한다.

```
Explore
→ Define
→ Specify
→ Design
→ Consistency Check
→ Ambiguity Check
→ Plan
→ Implement
→ Verify
→ Sync
```

---

# 21. 완료 보고

작업 완료 후 가능한 경우 다음을 정리한다.

## 변경 내용

무엇을 변경했는가?

# 22. 핵심 행동 원칙

### Understand Before Coding

코드보다 현재 시스템을 먼저 이해한다.

### Requirements First

모든 구현은 요구사항에서 시작한다.

### Scope Before Coding

무엇을 할지와 무엇을 하지 않을지를 명확히 한다.

### Do Not Assume

결정되지 않은 내용을 추측하지 않는다.

### Specify Before Implementing

코드를 작성하기 전에 기대 동작을 정의한다.

### Consistency Before Implementation

요구사항과 설계가 서로 일치하는지 먼저 검증한다.

### Simplicity First

현재 문제를 해결하는 가장 단순한 방법을 우선한다.

### Surgical Changes

필요한 부분만 변경한다.

### Plan Before Large Changes

큰 변경은 계획한 뒤 구현한다.

### Measure Before Optimizing

측정한 뒤 최적화한다.

### Verify Against Spec

Specification을 기준으로 결과를 검증한다.

### Keep Spec and Code in Sync

Specification과 실제 구현을 항상 일치시킨다.

# 23. 최종 SDD Flow

```
                  ┌─────────────┐
                  │   Explore   │
                  └──────┬──────┘
                         ↓
                  ┌─────────────┐
                  │   Define    │
                  │ 목적 / 범위 │
                  └──────┬──────┘
                         ↓
                  ┌─────────────┐
                  │   Specify   │
                  │ 기대 동작   │
                  └──────┬──────┘
                         ↓
                  ┌─────────────┐
                  │   Design    │
                  └──────┬──────┘
                         ↓
              ┌────────────────────┐
              │ Consistency Check  │
              │ 요구사항 ↔ 설계    │
              └─────────┬──────────┘
                        ↓
                  ┌─────────────┐
                  │    Plan     │
                  └──────┬──────┘
                         ↓
                  ┌─────────────┐
                  │  Implement  │
                  └──────┬──────┘
                         ↓
                  ┌─────────────┐
                  │   Verify    │
                  │ Spec 기준   │
                  └──────┬──────┘
                         ↓
                  ┌─────────────┐
                  │    Sync     │
                  │ Spec ↔ Code │
                  └─────────────┘
```

# 나의 SDD 한 문장 정의

**먼저 현재 시스템을 이해하고 요구사항과 범위를 명확히 한 뒤, Specification을 기준으로 설계·구현하며, 구현 결과를 다시 Specification과 비교하여 검증하고 변경된 요구사항과 코드를 지속적으로 동기화하는 개발 방식이다.**
