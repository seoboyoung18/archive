# H1 CPU 방어·잡기 대응 기준 검수

2026-10-03. C/G/S2 완료 `94c9eff` 뒤 사용자 “다음 진행하자”에 따라 후속 대전 보완의 근거를 확인했다. **현재 AI의 순수 공통 로직 재현이며 실제 사람의 플레이·난이도 평가가 아니다.** 게임 수치·전략·코드는 바꾸지 않았다. [AI-G 상세안](../specs/h1-ai-grab.md)은 이 결과를 바탕으로 작성한 승인 전 제안이다.

## 입력과 재현 방법

기존 `createMatch/startMatch`의 PLAYER400/CPU880, 체력100/100,60초·2선승, CPU 커서0에서 시작한다. 기존 `stepH1AiMatch`에 PLAYER 입력만 넣고 모든 경기·전투 판정은 그대로 실행한다. 위치/체력/시간/AI 상태를 도중에 주입하지 않는다. 현재 AI에 난수는 없으므로 각 정책을 **같은 초기값에서3회** 실행하고 전체 결과가 동일한지 비교했다. 여러 난수 시드나 인간 표본3명으로 보지 않는다.

- 무입력: 매틱 중립.
- 선 방어: 매틱 상대 반대 방향 유지. 실제 후진 이동을 포함한다.
- 앉은 방어: 매틱 아래+상대 반대 방향 유지.
- 접근·잡기 반복: 매틱 공개 거리96 밖이면 접근, 안쪽에서 자기 지상/free면 U/I 새 동시 누름, 다음틱 놓기. 상대의 미래 상태나 잡기 나이를 보고 재시도하지 않는다. 프레임 단위의 정밀 자동 입력이다.

KO 연출을 끝낸 뒤 공통 `nextRound`로 진행한다. 동률은 엔진 규칙대로 같은 라운드를 다시 하되5번째 시도에서 **관찰만 종료**하고 승자를 만들지 않는다. 아래 초는 전투F/60이며 KO 연출18F·수동 전환 대기·브라우저 벽시계는 제외한다.

```powershell
node --experimental-strip-types docs/reviews/evidence/h1-ai-baseline.mjs
```

[재현 스크립트](evidence/h1-ai-baseline.mjs)는 `94c9eff`의 게임 코드를 대상으로 보존했다. [전체 결과 JSON](evidence/h1-ai-baseline.json)에 소스 해시·정책·라운드별 통계·전 접촉 사건·잡기 타임라인을 담았다. 이후 AI 코드가 바뀌면 이 결과를 새 코드의 결과로 재사용하지 않는다.

보존 경로에서도 실행해 원본 결과 JSON과 SHA256까지 일치함을 확인했다. 문서57개·상대 링크373개 누락0·공백 검사를 통과했고, [지정 Notion](https://app.notion.com/p/3eca2fe05e6881c29eabd7435a688947)의 기준 재현/후속 제안 기록은 저장 후 재조회로 확인했다.

## 결과

두 승부 라운드는 같은 입력에 같은 결과를 보였고, 앉은 방어는5회 모두 같은 동률이었다. 각 정책의3회 재실행도 완전히 일치했다.

| PLAYER 정책 | 경기 승수 P:CPU | 라운드 종료 HP P:CPU | 라운드 전투 시간 | 관찰 |
|---|---:|---:|---:|---|
| 무입력 | 0:2 | 0:100 | 483F / 8.05초 | CPU 기본기8타 명중 |
| 선 방어 유지 | 0:2 | 0:100 | 609F / 10.15초 | CPU 앉은 약발13회, 모두 명중 |
| 앉은 방어 유지 | 0:0 | 100:100 | 3600F / 60초 | CPU89타 모두 방어, 동률 재경기5회 |
| 접근·잡기 반복 | 2:0 | 92:0 | 480F / 8초 | 잡기7시도·6성공/충격, CPU 풀기0 |

선 방어는 하단을 막지 못하는 기존 규칙대로 피해를 받았다. 아래+뒤는 현재 CPU가 선택하는 일반/하단을 모두 막는다. 선 강발은 앉은 피격 범위에 닿지 않아 후보에서도 빠진다. 방어가 깨지지 않는 결과는 공통 방어 버그가 아니라 현재 승인된 기술 선택의 한계다.

## 반복 잡기의 경계

F는 처리 후 `combat.frame`이다. 첫 처리 틱이F1이고 성공 관계의 첫 프레임이H0다.

| 시점 | 실제 결과 |
|---|---|
| F49 | PLAYER 첫 잡기 시도와 CPU 약손 시작 |
| F55 | CPU 약손 피해8이 잡기보다 우선해 첫 시도 취소. PLAYER92 |
| F78 → F84 | 두 번째 시도 → 첫 성공 잡기H0 |
| F120 | H36 바닥 충격, CPU100→82 |
| F138 | H54 PLAYER 복귀, 거리 밖이면 다시 접근 |
| F150 | 이전 성공H66에서 새 잡기 시도. CPU는 기존 다운/기상 잠금 |
| F156 | 기존 대상H72에 새 잡기의 유효 구간이 만나 재성립. 새H0 |
| F192 | 기존 기준H108, 새 성공H36에서 다음 바닥 충격 |

이후 성공F228/300/372/444, 충격F264/336/408/480으로 이어졌다. F156 처리 직전 CPU는 이전 잡기H71·판단 잔여1이라 중립을 내며, 다음 판단 기회에는 이미 새 잡힘이다. **현재 CPU도 준비 중 잡기를 타격으로 끊을 수 있으나, 성립 뒤에는 풀기 선택이 없고 이번 입력에서 기상 경계의 반복을 벗어나지 못했다.**

기상 무적·자동 회피·잡기 피해 감소를 임의로 넣는 근거로 사용하지 않는다. 다음 보완은 기존 공통 풀기와 잡기를 CPU도 선택하는 최소 범위로 제안한다. 실제 사람은 이 자동 입력처럼 매F 정확히 접근·재잡기를 하지 않을 수 있다.

## 정합성·한계·후속

- 내장 브라우저의 현재 `match.html`은 이전 검수의F218·정지·PLAYER70/CPU100·음량30% 상태였다. 이번 턴에 조작 상태를 바꾸거나 새로운 실제 대전을 완료하지 않았다. 위 표의 결과는 브라우저 플레이 결과로 보고하지 않는다.
- 독립 명세/코드 검토에서 `guard` 대상은 공통 잡기 불가, 두 손 공격 배열만으로는 CPU 잡기 불가, 기존 잡기 잠금은 관찰도 생략하는 세 가지 연결 조건을 확인했다. 새 정책은 상대free 자격·명시적인 겹친 손 이벤트·붙잡힌 대상의 제한된 관찰 예외를 필요로 한다.
- 기존12F 판단 시계에서 잡힘 직후 잔여가0~11이면 첫 풀기 입력은H1~12다. 반응성 CPU 풀기를 위해 PLAYER H0 입력을 미리 읽거나 새 프레임 특례를 만들 필요가 없다.
- 최종 독립 읽기 검토에서 구현을 막는 설계 모순은 발견하지 못했다. 관찰H11→적용H12와 관찰H12→적용H13을 구분하고 대상H19 그림 전환과 혼동하지 않도록 초안을 명확히 했다. 기존 공통 hold/impact/escape 사건을 재사용하므로 새 음원도 필요하지 않다. 이는 새 AI 구현 통과가 아니다.
- 출력기기 음질·소리 구분·실제 인간 방어/풀기 난이도·독립 Chrome/Edge는 여전히 미확인이다. 기준 스크립트의 반복 검증을 새 AI 구현 검사나 전체260개 회귀 재실행으로 보고하지 않는다.
