# Git 컨벤션 · Dimension Fight

2026-10-02 사용자 결정: **1인 개발을 기준으로 `main`에서 직접 작업하고 검증 후 커밋·push한다.** 앞서 검토한 `dev` 통합 브랜치와 매 작업의 기능 브랜치·PR 의무는 이 결정으로 대체한다.

## 작업 흐름

1. 현재 브랜치·변경 파일·원격 상태와 관련 명세를 확인한다.
2. [SDD](SDD.md)에 따라 필요한 명세·코드·에셋을 함께 수정한다.
3. 변경 범위에 맞는 검사와 테스트를 수행한다. 확인하지 못한 사항은 기록한다.
4. 작업 단위로 커밋하고 `main`에 일반 push한다. 원격의 커밋과 로컬 상태를 확인한다.
5. 개발일지와 사용자 지정 Notion 트러블슈팅 기록을 유지한다.

- 평소에는 `main` 하나로 작업한다. `dev`를 생성하거나 기본 브랜치를 바꾸지 않는다.
- 큰 실험이나 구조 변경을 분리할 필요가 있을 때만 임시 브랜치를 사용한다. 사용할 경우 기능은 `feature/`, 수정은 `fix/`, 리팩터링은 `refactor/`와 작업명을 조합한다. 실제 이슈가 있으면 `feature/이슈번호-기능명`처럼 번호를 연결한다.
- 이슈·PR·타인 승인은 일상 작업의 필수 절차가 아니다. 필요한 작업에서 선택적으로 사용하며 해당 작업에 적용되는 저장소 보호 규칙은 따른다.
- 명세에 대한 사용자 확인이 필요한 작업은 기존 SDD 승인 조건을 유지한다. Git 절차를 줄인 것이 미승인 기능의 구현 허용을 뜻하지 않는다.
- 커밋을 되돌릴 지점으로 유지한다. 이미 공유된 이력을 덮어쓰는 강제 push는 기본 작업 흐름에 포함하지 않는다.
- 기존 기능 브랜치는 보관한다. 이번 전환에 불필요한 브랜치 삭제·이력 재작성은 하지 않는다.

## 커밋 메시지

형식은 `태그: 작업 내용 (#이슈번호)`다. 태그 첫 글자를 대문자로 쓰고 콜론 뒤에 한 칸을 띄운다. 이슈 번호는 선택 사항이며 실제 연결할 이슈가 있을 때 기재한다. 작업 내용의 언어는 강제하지 않는다.

| 태그 | 용도 |
|---|---|
| `Feat` | 기능 추가 |
| `Fix` | 버그·오류 수정 |
| `Add` | 코드 변경 없이 에셋 등 파일 추가 |
| `Remove` | 파일 삭제 |
| `Docs` | 명세·README 등 문서 작업 |
| `Refactor` | 기능 변경 없이 코드 구조 개선 |
| `Test` | 테스트 추가·수정 |
| `Style` | 동작에 영향을 주지 않는 포맷·주석 변경 |
| `Chore` | 설정·의존성·파일 이동 등 기타 작업 |

예: `Fix: H1 강공격의 반대 손발과 전신 회전 보완`

코드와 에셋을 함께 연결한 기능 구현은 `Feat`, 그림 파일만 추가한 작업은 `Add`처럼 실제 변경 목적에 맞춘다. 비밀키·로컬 환경 파일·빌드 결과·의존성 폴더는 커밋하지 않는다.

## 기존 작업의 main 반영

- 전환 전 원격 `main`은 `21e1332`, 로컬 작업은 `f4181be`까지 17개 커밋이었다.
- 기존 17개 커밋의 내용·순서·SHA를 그대로 보존한다. 이전의 소문자 태그는 당시 기록으로 유지하고 새 커밋부터 위 규칙을 적용한다. 앞서 작성한 메시지 재작성 제안은 채택하지 않는다.
- 컨벤션 문서 변경을 별도 `Docs` 커밋으로 남기고 `main`을 fast-forward한다. squash나 rebase로 기존 작업 이력을 바꾸지 않는다.
- push 결과는 [개발일지](devlogs/2026-10-02.md)에 실제 확인한 내용으로 기록한다. 반영 완료를 게임의 전체 기능·모션 품질 완료로 간주하지 않는다.
